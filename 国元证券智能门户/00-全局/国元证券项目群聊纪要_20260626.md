## 三、人员信息接口调整（yglb / zzzt 字段）

### 需求变更

#### 3.1 员工类别（yglb）
- **Michael（葛鹏飞）**：人员信息接口需加 `yglb`（员工类别）字段，不需要在企微展示。
- 字典项：

| 编码 | 名称 |
|------|------|
| 1 | 正式员工 |
| 2 | 劳务派遣员工（业务辅助岗） |
| 3 | 劳务派遣员工（后勤保障岗） |
| 4 | 经纪人 |
| 5 | L序列理财顾问 |
| 6 | 财富顾问 |
| 7 | 外部检查人员 |
| 8 | 实习生 |
| 9 | 应聘人员 |
| 10 | 外部企业伙伴账户 |

- **Y 确认**：字段是数字类型。

#### 3.2 在职状态（zzzt）
- **Michael**：再加 `zzzt`（在职状态）字段。
- 字典项：

| 编码 | 名称 |
|------|------|
| 0 | 在职 |
| 1 | 离职 |
| 2 | 内退 |
| 3 | 退休 |
| 4 | 解聘 |
| 5 | 长期病假 |

- **Y 确认**：不同步到企微，只存储。

### 决议

#### 禁用逻辑
- **hackee**：在职后离职/退休的，后台先做禁用，数据不丢。
- **Michael**：不在职状态 0/2/5 的可以禁用吗？
- **Y**：可以实现。
- **hackee**：门户账户也应该有这些状态和对应的禁用逻辑，门户跟企微账户逻辑一致。

#### 同步规则（最终确认）
- **Michael**：同步到企微的条件：
  - 员工类别 ∈ {1, 2, 5, 6, 8}
  - 在职状态 ∈ {0, 2, 5}（即在职/内退/长期病假）

#### 删除逻辑
- **hackee**：企微账户同步**不要有删除账户的逻辑**，人员历史会话数据需要保留。
- 如确实需要删除，由管理员手工操作。
- **Y**：没有删除人员的逻辑。

#### 员工类别同步方式
- **Michael**：员工类别字段可作为**标签**同步到企微（之前开会与王工交流过）。

## 六、统一待办 vs 统一消息接口区分

### 问题
- **hackee**：
  1. 待办跟消息的接口是同一个吗？
  2. API 接口文档看不清，消息接口是不是只需创建不需关闭？
  3. 有没有针对消息接口的说明？

### 回应
- **zZZ（张沿）**：
  - 统一待办中心的消息和待办是**绑定的**，待办/待阅都会在系统和企微分别发一条消息卡片。
  - **单独的消息接口**通过另一个应用发出，不和待办共用。
  - 待办和消息是**两个独立的接口**。

### 确认
- **hackee**：统一待办和统一消息是两个接口 —— 各应用推送消息提醒（不是待办）。
- **zZZ**：对的，这个就不是待办了。

### 状态
- 消息接口文档待张沿整理后发群。

## 十一、风险关注

1. **首次初始化数据丢失**：测试账号清空重建，需确保后续增量同步不影响生产数据。
2. **同步覆盖用户数据**：邮箱绑定丢失说明增量同步可能覆盖用户自主修改的数据，需排查同步逻辑。
3. **单节点风险**：中间登录程序目前单节点，挂了影响自动登录，需尽快完成高可用部署。
4. **接口文档缺失**：消息接口文档不清，影响第三方应用对接进度。
